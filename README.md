# permission-system

Расширение Pi для data-ops. Один пакет загружает Gate и Auto Review. Требуются Node.js ≥ 24 и Pi 1.5.x.

## Установка

После публикации выполните из корня целевого проекта:

```sh
pi install -l npm:permission-system@1.0.4
```

При разрешённом `postinstall` команда с `-l` создаёт только отсутствующие `config.json` в `.pi/extensions/pi-permission-system/` и `.pi/extensions/pi-permission-auto-review/` проекта. Без `-l` те же файлы создаются в `<agentDir>/extensions/`, где `<agentDir>` — `PI_CODING_AGENT_DIR` или, по умолчанию, `~/.pi/agent`. Установка и обновление не заменяют существующие файлы и не сливают их с примерами. Локальная установка не меняет глобальные файлы, но в доверенном проекте правила из скопированных примеров имеют приоритет над глобальными.

В npm 12 для автоматического копирования разрешите **точную версию** в `allowScripts` перед установкой: добавьте `"permission-system@1.0.4": true` в этот объект в `<проект>/.pi/npm/package.json` для `-l` или в `<agentDir>/npm/package.json` для глобальной установки. Если скрипт не разрешён или указан `--ignore-scripts`, пакет не обходит запрет. Временный npm-префикс Pi и обычная установка вне префиксов Pi конфиги не создают.

Без lifecycle-скриптов конфиги можно установить явно. Из корня проекта для локального npm-пакета выполните:

```sh
node .pi/npm/node_modules/permission-system/scripts/install-configs.mjs --project
```

Для глобальной установки вызовите `node <agentDir>/npm/node_modules/permission-system/scripts/install-configs.mjs --global`, подставив путь к профилю. `pi install -l <локальный-путь>` лишь подключает каталог и не запускает `postinstall`: из корня проекта выполните `node <локальный-путь>/scripts/install-configs.mjs --project`. Запуск расширения и `/reload` не создают и не восстанавливают конфиги.

Оператору: если старые `@gotgenes/pi-permission-system` и `@mzwing/pi-permission-auto-review` уже подключены, замените их новым пакетом, а не загружайте оба комплекта одновременно. Не удаляйте конфиги вслепую: сохранённые глобальные и доверенные проектные правила накладываются на встроенную политику. Откройте доверенный проект и выполните `/reload`. `/permission-auto-review show` показывает эффективные настройки; готовность зарегистрированного ревьюера отображается в строке состояния.

## Что проверяется

- При выключенном YOLO чтение файлов проекта и распознанных внешних файлов по умолчанию разрешено, в том числе через симлинк. Обычная внешняя запись требует отдельного решения оператора по фактическому пути; одобрение модели его не заменяет. Сохранённые глобальные и доверенные проектные правила могут переопределить эти значения.
- В собранном Gate запись управляемого черновика `<agentDir>/pi-plan-mode/drafts/<UUID v4>/plan.md` по умолчанию освобождена от запросов `path_write` и `external_directory_write`. Исключение действует только для физического файла текущего профиля: каталог черновика не должен быть симлинком, а существующий файл должен быть обычным файлом без дополнительных жёстких ссылок. В `.pi` правило `path_write` запрещает изменение конфигов `pi-permission*`; для остальных файлов действуют обычные проверки. Сам инструмент `write` или `edit` по-прежнему может потребовать авторевью или ручного решения. JSON в `examples/` сам по себе исключение для черновика не включает.
- Запись, запуск скрипта и вызов неизвестного инструмента требуют решения. Ревьюер оценивает **эффект**, а не имя команды: «сохрани отчёт» может согласовать запись, «покажи статистику» — нет. Если существенный код не виден, политика требует отказа с `NEEDS_EVIDENCE`. При недоступности ревьюера `ask` переходит оператору; без ответа действие не выполняется.
- При выключенном YOLO для `hdfs dfs -ls /` Pi сначала запрашивает подтверждение внешнего пути `/`, затем отправляет команду на авторевью: без `fs.defaultFS` нельзя считать путь гарантированно удалённым и эффект только чтением. Разрешение подтверждённого внешнего чтения не означает автоматического разрешения shell-команд. `hadoop fs -rm /data` запрещён до авторевью, в том числе внутри распознанного пайплайна.
- Пресет `codex` задаёт способ проверки, а не модель. Ревьюер передаёт сведения о действии и контекст сессии выбранному провайдеру. По умолчанию `yoloMode` выключен; единственное звено перед ручным решением — `auto-review`.

### Модель авторевьюера (с 1.0.1)

По умолчанию ревьюер использует провайдера и модель текущей сессии Pi. После `/model` следующий запрос проверяет уже новая модель; `/reload` не нужен.

Для отдельного ревьюера откройте `/permission-auto-review` и задайте `Provider` и `Model` в настройках проекта или пользователя. `/permission-auto-review show` покажет результат. Явные значения в доверенном проекте приоритетнее глобальных. Если задано только одно поле, второе наследуется; если получившаяся пара недоступна, запрос передаётся оператору, а не другой модели.

**При обновлении с 1.0.0:** уже сохранённые `provider` и `model` остаются переопределениями. Чтобы вернуться к модели сессии, выберите `Use inherited value` для `Provider` и `Model` в тех областях, где они заданы, затем `Save changes`. Не сбрасывайте весь конфиг: в нём могут быть собственные правила проверки.

### YOLO mode

YOLO выключен по умолчанию. Чтобы включить его для доверенного проекта, в интерактивном Pi откройте `/permission-system` и переключите `YOLO mode`. Команда `/permission-system show` показывает текущее значение, строка состояния — индикатор `yolo`. Повторное переключение выключает режим; `/permission-system reset` также выключает его для текущего доверенного проекта в интерактивной сессии.

**Внимание:** при включённом YOLO все запросы `ask` автоматически одобряются без авторевью и ручного подтверждения, в том числе внешние пути, непрозрачные shell-команды и запросы дочерней сессии, переданные родителю с включённым YOLO. Явные правила `deny` по-прежнему блокируют вызовы. Это не меняет защиту провайдера Pi и не превращает проверку в песочницу.

Выбор сохраняется отдельно для каждого канонического пути проекта в домашнем каталоге агента Pi, вне checkout, и действует на следующих ходах, после `/reload` и нового запуска. Симлинк на тот же каталог проекта обозначает тот же выбор. Старые или статические значения `yoloMode` в глобальном и проектном JSON игнорируются: включить режим можно только через панель в интерактивном доверенном проекте. В недоверенном проекте режим выключен.

### Ручной режим

В интерактивном терминале Pi оператор вводит:

```text
/permission-auto-review off
```

При выключенном YOLO новые `ask` идут оператору без обращения к модели. Это не «разрешить всё»: `deny` остаётся запретом. В ручном режиме оператор сам проверяет, например, что делает Python-скрипт. Конфиг не изменяется. `/reload` или новая сессия включает авторевью снова.

### Границы

Это проверка вызовов, а не песочница для процессов, сети и MCP. Оператор отдельно защищает управляющие файлы и код расширений, если они загружаются вне `.pi`. Контекстные файлы не являются согласием пользователя. Не давайте агенту менять механизм проверки.

`@gotgenes/pi-subagents` необязателен и не устанавливается этим пакетом. При его использовании не исключайте **`permission-system`** из загрузки дочерними сессиями. Одобрение запуска субагента не разрешает его последующие вызовы; неразрешённый дочерний запрос передаётся родителю. У родительского ревьюера нет полного транскрипта ребёнка.

## Локальная проверка и выпуск

```sh
npm ci
npm test
npm pack
```

Сборка включает код `@gotgenes/pi-permission-system@42.1.0` и `@mzwing/pi-permission-auto-review@1.0.2`, правила из `examples/*.config.json` и лицензии upstream. Тесты не требуют аккаунта LLM или кластера Hadoop. Для публикации проверенного архива: `npm publish ./permission-system-1.0.4.tgz --tag latest`.
